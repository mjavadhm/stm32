# بازبینی کیفیت پروژه (تا پایان M3)

آخرین بازبینی: ۲۰۲۶-۰۸-۱۲ — پس از رفع سه باگ بلاکر M3 (نبود توابع دیتاشیت، ناهماهنگی کلید `hardware`، نشت event loop در Celery).

این سند دو کار می‌کند:

1. ده موردی را فهرست می‌کند که کیفیت خروجی سیستم را بالا می‌برد.
2. مشخص می‌کند کدام‌ها **پیش‌نیاز واجب M4** بودند و همین حالا پیاده شدند، و کدام‌ها آگاهانه به بک‌لاگ رفتند.

معیار «واجب برای M4»: طبق `docs/architecture.md`، M4 یعنی ایجنت‌های CubeMX و Firmware؛ یعنی از روی `implementation_order` کد تولید می‌شود. هر چیزی که کیفیت آن کد را تعیین می‌کند یا خطا را بی‌صدا به آن مرحله منتقل می‌کند، واجب است. بقیه، هر چقدر هم مفید، بک‌لاگ است.

## ۱. `grounded` واقعیت را نمی‌گفت ✅

**مشکل.** در `answer_hardware_question` این بود:

```python
"grounded": context.available and not context.is_empty
```

یعنی «بازیابی چیزی برگرداند». با `top_k` ثابت، بازیابی تقریباً همیشه چیزی برمی‌گرداند — حتی وقتی هیچ‌کدام به سؤال ربط ندارند. پس `grounded=True` عملاً یعنی «PageVault بالا بود».

**چه شد.** دو مفهوم از هم جدا شدند:

- `citations`: منابعی که بازیابی **پیشنهاد داد**.
- `cited`: منابعی که در متن پاسخ **واقعاً ظاهر شدند** (`[c for c in citations if c in answer]`).
- `HardwareFinding.verified` = `bool(cited)`، و `HardwareFindings.coverage` = نسبت یافته‌های verified.

اگر منبعی بازیابی شد ولی مدل به آن اشاره نکرد، یک warning صریح ثبت می‌شود: `"<topic>: sources were retrieved but the answer cited none of them"`. ایجنت معماری هم اگر `grounded and not verified` بود، طراحی را «unverified» علامت می‌زند.

`grounded` عمداً حذف نشد؛ معنای درستِ خودش را دارد: «آیا اصلاً منبعی در دسترس بود؟».

## ۲. اعتبارسنجی ارجاع per-topic ✅

**مشکل.** `_enforce_evidence` با `known = set(hardware.citations)` کار می‌کرد — اجتماع همه‌ی منابعِ همه‌ی سؤال‌ها. چون M3 برای هر پریفرال یک بازیابی جدا می‌زند، ارجاعی که برای USART2 آمده بود می‌توانست روی تصمیم SPI1 بنشیند و از فیلتر رد شود.

**چه شد.**

- `HardwareFindings.citations_for(topic)` و `_allowed_citations(hardware, peripheral)` اضافه شدند (تطبیق دقیق، بعد تطبیق زیررشته‌ای).
- ارجاع خارج از `known` → مثل قبل حذف و به `assumptions` منتقل می‌شود، **و** حالا یک warning ماشین‌خوان می‌دهد: `unverifiable citation dropped`.
- ارجاعی که در `known` هست ولی برای topic دیگری بازیابی شده → نگه داشته می‌شود ولی flag می‌خورد. حذف نمی‌کنیم چون فایل‌های مشترک (HAL DMA، clock tree) واقعاً چند پریفرال را پوشش می‌دهند.
- در پرامپت هم صریح شد: زیر هر topic خط `Allowed references for <topic>: ...` می‌آید.
- یک no-op قدیمی هم اصلاح شد: `citations = [c for c in hardware.citations if c in used] or used` که شاخه‌ی `or used` هرگز چیز جدیدی اضافه نمی‌کرد.

## ۳. retry روی قرارداد JSON ✅

**مشکل.** تصمیم #۳ در `docs/architecture.md` نوشته: «JSON Schema + اعتبارسنجی Pydantic + retry». دو تای اول پیاده بود؛ retry نبود. اولین پاسخ خراب مستقیم به مسیر degraded می‌رفت. مدل‌های محلی دقیقاً روی پاسخ‌های طولانی از schema خارج می‌شوند و M4 پاسخ‌های خیلی طولانی‌تری می‌خواهد.

**چه شد.** ماژول جدید `app/agents/base.py` با `request_contract(llm, model, messages)`:

- پاسخ خراب → خطای parser به خود مدل برگردانده می‌شود («این پاسخت parse نشد، فقط JSON بده») به‌همراه کپیِ کوتاه‌شده‌ی پاسخ قبلی (سقف ۲۰۰۰ کاراکتر تا یک خروجی رَم‌کرده دوباره کامل ارسال نشود).
- تعداد تلاش‌ها با `LLM_CONTRACT_RETRIES` (پیش‌فرض ۱) کنترل می‌شود.
- اگر همه‌ی تلاش‌ها شکست خورد، `ContractError` بالا می‌رود و تصمیمِ degrade با خودِ ایجنت می‌ماند (رفتار فعلی حفظ شد).

هر سه ایجنت requirements، architecture و (به‌زودی) firmware از همین مسیر رد می‌شوند.

## ۴. دو قاتل خاموش ✅ (ابزار تشخیص)

**الف) فیلتر `family`.** در `PageVaultClient.search` این هست:

```python
text_filters = {"family": family}
```

اگر chunkهای ایندکس‌شده فیلد `family` نداشته باشند، همه‌ی جستجوها صفر برمی‌گردانند، همه‌ی ایجنت‌ها از حافظه‌ی مدل جواب می‌دهند، و `make kb-check` (که فقط `/health` را می‌زند) سبز می‌ماند.

**چه شد.** `backend/scripts/kb_probe.py` + هدف `make kb-probe`: همان کوئری را یک‌بار با فیلتر و یک‌بار بدون فیلتر می‌زند، تعداد hitها را در چهار کانال چاپ می‌کند و اگر «بدون فیلتر > ۰ و با فیلتر == ۰» بود با کد خروج ۱ شکست می‌خورد. برای CI هم قابل استفاده است.

**ب) `num_ctx` در Ollama.** پنجره‌ی پیش‌فرض ۲۰۴۸ توکن است و ollama بی‌صدا از چپ می‌بُرد؛ یعنی `RAG_CONTEXT_MAX_CHARS=12000` عملاً دور ریخته می‌شود و مدل فقط انتهای پرامپت را می‌بیند. این کد نیست، پیکربندی است: هنگام ساخت مدل محلی باید `PARAMETER num_ctx 8192` (یا بیشتر) ست شود. کنترل `LLM_MAX_TOKENS` هم اضافه شد (۰ = پیش‌فرض provider) تا سمت خروجی هم سقف داشته باشیم.

ضمناً `RAG_MIN_SCORE` اضافه شد (پیش‌فرض ۰ = خاموش) تا بعد از کالیبراسیون بشود snippetهای بی‌ربط را دور ریخت. اسنیپت با score صفر حذف نمی‌شود، چون «امتیاز گزارش نشده» با «امتیاز صفر» یکی نیست.

## ۵. قراردادها برای M4 ✅ (schema v2)

کدژنراتور نمی‌تواند از یک plan بدون شواهد، کد قابل‌دفاع بسازد. تغییرات `contracts.py`:

| فیلد جدید | کجا | چرا |
|---|---|---|
| `cited` | `HardwareFinding` | تفکیک «منبع پیشنهادشده» از «منبع استفاده‌شده» |
| `citations` | `Module` | هر ماژول به منبع خودش وصل است |
| `files`, `citations` | `ImplementationStep` | ایجنت firmware دقیقاً با همین منابع پرامپت می‌شود |
| `evidence` | `Architecture` | نگاشت topic → منابع، برای دنبال‌کردن زنجیره‌ی requirement → evidence → decision → file |

همچنین:

- `SCHEMA_VERSION = 2` و `SUPPORTED_SCHEMA_VERSIONS = {1, 2}`. همه‌ی فیلدهای جدید default دارند، پس ردیف‌های v1 هنوز parse می‌شوند.
- تابع `parse_stored(model, data)` برای خواندن قراردادی که قبلاً نوشته شده (state بین nodeها و `TaskRun.result` قدیمی). نسخه‌ی ناشناخته **بلند** fail می‌کند، نه اینکه بی‌صدا به یک آبجکت خالی تبدیل شود و طراحی همه‌ی ارجاع‌هایش را از دست بدهد.
- اگر یک step هیچ ارجاعی نداشت، `_infer_step_citations` به‌صورت قطعی (نه با مدل) از روی نام topicهای موجود در عنوان/شرح/ماژول‌های step، شواهد را می‌چسباند؛ حداکثر ۴ تا.

## ۶. eval harness ✅

بدون عدد، «کیفیت بهتر شد» یک حس است. `backend/evals/` اضافه شد:

- `cases.json`: چند درخواست نماینده (SPI+DMA، UART+FreeRTOS، I2C، درخواست مبهم بدون MCU).
- `run_eval.py`: مسیر requirements → datasheet → architecture را مستقیم اجرا می‌کند (بدون DB و Celery) و این‌ها را می‌سنجد: نرخ قرارداد معتبر، coverage ارجاع سخت‌افزاری، نرخ ارجاع توهمی (شمارش `unverifiable citation dropped`)، نرخ hit بازیابی، تعداد stepهای دارای شواهد، اجراهای degraded، و latency هر مرحله.
- خروجی: یک JSON در `backend/evals/results/<timestamp>.json` + جدول Markdown در stdout.

اجرا: `make eval`. این عددها baseline قبل از M4 هستند؛ بعد از هر تغییر پرامپت دوباره بگیرید.

## ۷. `open_questions` هیچ‌وقت پرسیده نمی‌شود ⏳

ایجنت requirements سؤالات باز را استخراج می‌کند، ایجنت معماری همان‌ها را در پرامپت می‌بیند، و بعد… هیچ. سیستم به‌جای پرسیدن، فرض می‌سازد. راه‌حل: یک gate انسانی بین requirements و architecture + checkpointer پستگرسِ LangGraph تا اجرا واقعاً بتواند متوقف و از سر گرفته شود. عمداً به بعد از M4 موکول شد چون به تغییر مدل داده و UI نیاز دارد، نه به کیفیت تولید کد.

## ۸. observability روی فراخوانی‌های LLM ⏳

یک جدول `AgentCall` (agent، model، prompt_version، tokens، latency، retries، citations_offered/used) + لاگ ساخت‌یافته‌ی JSON. وقتی کیفیت افت کند، بدون این نمی‌شود فهمید پرامپت عوض شده یا مدل. پیشنهاد: همراه با ایجنت‌های M4 اضافه شود، چون آن‌ها بیشترین توکن را مصرف می‌کنند.

## ۹. تست‌ها یک لایه پایین‌تر از باگ‌ها ⏳/✅

باگ‌های واقعی M3 (کلید `hardware`، توابع جاافتاده) از تست‌های واحد رد می‌شدند. تست e2e درون‌حافظه‌ای (SQLite + گراف واقعی + FakeLLM + MockTransport) هنوز بک‌لاگ است، اما `backend/tests/test_m4_ready.py` اضافه شد و رفتارهای جدید را پوشش می‌دهد: `cited`/`verified`/`coverage`، اعتبارسنجی per-topic، warningِ ارجاع قرض‌گرفته‌شده، پرکردن خودکار شواهد step، نگاشت `evidence`، گاردِ نسخه‌ی schema، و هر دو مسیر retry (موفق و شکست‌خورده).

## آنچه M4 حالا می‌تواند روی آن بنا شود

1. `Architecture.implementation_order` دیگر فقط یک لیست کار نیست: هر step فایل‌ها و منابعش را دارد. ایجنت firmware می‌تواند step به step پیش برود و برای هر step فقط شواهد همان step را در پرامپت بگذارد.
2. `Architecture.evidence` نگاشت topic → منابع را نگه می‌دارد؛ اگر مدل برای stepی منبع نداد، سیستم به‌صورت قطعی پرش می‌کند.
3. `request_contract` آماده است؛ ایجنت‌های CubeMX و Firmware از روز اول retry دارند.
4. `parse_stored` جلوی خواندن قرارداد ناسازگار را می‌گیرد — مهم است چون M4 خروجی اجراهای قبلی را می‌خواند.
5. `make eval` یک baseline عددی می‌دهد که بعد از افزودن دو ایجنت جدید بشود با آن مقایسه کرد.

## ترتیب پیشنهادی بک‌لاگ

1. بازیابی دومرحله‌ای با `RagContext.identifiers` (الان دور ریخته می‌شود؛ ارزان‌ترین بهبود کیفیت بازیابی).
2. جدول `AgentCall` + لاگ ساخت‌یافته.
3. تست e2e درون‌حافظه‌ای.
4. HITL روی `open_questions` + checkpointer.
5. جدا کردن `warnings` از بدنه‌ی قرارداد (الان کنار فیلدهای contract در state می‌نشیند و `PipelineState`/worker/frontend باید هماهنگ تغییر کنند).
6. `UniqueConstraint(project_id, agent_name)` روی `TaskRun` + ستون `attempt`.
7. حذف سرویس بلااستفاده‌ی qdrant، پین‌کردن `langgraph<1.0`، افزودن `next build` و `npm ci` به CI.
